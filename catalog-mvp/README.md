# EquipLens: тестовий MVP 3D-каталогу обладнання

> **Тимчасове сховище.** Остаточний дім: третя вкладка застосунку EquipLens, репозиторій [`Konst-Andre/equiplens`](https://github.com/Konst-Andre/equiplens). Тут усе лежить окремо, щоб випробувати підхід, не чіпаючи продукт. Файл написано так, щоб агент без доступу до історії розмови зрозумів, що це, навіщо і як працює.

## 0. Коротко

- **Що:** каталог мерч-обладнання з 3D-моделями для польового застосунку EquipLens. У сітці лише картинки-постери, 3D вмикається для однієї моделі за тапом.
- **Де:** папка `catalog-mvp/` у репозиторії `Konst-Andre/sandbox`; сторінка `https://konst-andre.github.io/sandbox/catalog-mvp/`.
- **Як додається модель:** власник кладе сирий GLB з Meshy у `catalog-mvp/inbox/`, бот (GitHub Actions) приблизно за 40 с оптимізує його, робить постер і оновлює `catalog.json`, Pages показує картку.
- **П'ять пасток (деталі в розділі 5):** (1) `model-viewer` не вмикає декодер meshopt сам; (2) оптимізований GLB має квантовані UV, а скрипт постера їх не читає без `dequantize`; (3) через сайт GitHub можна завантажити файл лише до 25 МіБ; (4) `equiplens` має власні правила й гейт-валідатор; (5) у `equiplens/data/` уже є свій `catalog.json`.
- **Що далі:** перенесення в EquipLens (розділ 7). Адмін-режим для додавання й видалення прямо з сайту свідомо відкладено (розділ 8).

## 1. Контекст і історія

Власник розробляє EquipLens: польовий нотатник потреби в обладнанні аптек (PWA, один HTML-файл). Третя вкладка має стати каталогом обладнання: які типи мерч-обладнання існують для кожного бренду, щоб представник міг зайти й подивитися, як воно виглядає. Каталог розрахований на 40-60 типів обладнання.

## 3. Структура

| Шлях | Роль |
|---|---|
| `catalog-mvp/index.html` | уся логіка сторінки: `render()` будує сітку, `openViewer()` створює живий `<model-viewer>`, `loadMV()` підтягує бібліотеку при першому відкритті |
| `catalog-mvp/catalog.json` | дані каталогу: `id`, `brand`, `name`, `glb`, `poster`, `sizeMB`. Бот оновлює запис за `id` |
| `catalog-mvp/models/` | оптимізовані GLB |
| `catalog-mvp/posters/` | WebP-постери для сітки (близько 40-60 КБ) |
| `catalog-mvp/inbox/` | вхід для сирих GLB (правила імен у `inbox/README.md`) |
| `catalog-mvp/scripts/process_inbox.py` | обробка inbox: головний скрипт бота |
| `catalog-mvp/scripts/poster.py` | програмний рендер постера (numpy, trimesh) |
| `catalog-mvp/scripts/optimize.sh` | ручна оптимізація одного GLB (запасний шлях) |
| `.github/workflows/catalog-inbox.yml` | workflow бота: запуск на push у `catalog-mvp/inbox/` і вручну |
| `catalog-mvp/scripts/catalog-inbox.workflow.yml` | резервна копія workflow, нічого не запускає |

Сторінку відкривати лише через http(s), не як `file://`: `fetch('catalog.json')` і завантаження GLB з файлу не працюють.

## 4. Як це працює

### 4.1 Додавання моделі (основний шлях)

1. У Meshy згенерувати модель із текстурою. 2K і 4K коштують однаково, але сирий GLB 4K (близько 34 МБ) не пройде через сайт GitHub (ліміт 25 МіБ), тому для цього шляху обирати 2K.
2. Назвати файл латиницею: `Бренд__Назва.glb` (два підкреслення), наприклад `Durex__DUR_Tower.glb`. Підкреслення в назві стають пробілами, зайві пробіли на початку, в кінці й подвійні прибираються. Необов'язковий файл `<те саме ім'я>.json` з полями brand, name, yaw: `yaw` це кут огляду постера в градусах (за замовчуванням 140, підібраний під Nurofen).
3. На github.com: `sandbox`, `catalog-mvp`, `inbox`, Add file, Upload files, коміт у `main`.
4. Workflow `Catalog inbox` (вкладка Actions) запускається сам. Приблизно за 40 с з'являється коміт `catalog-bot: оброблено <id>`, а сирий файл із inbox видаляється.
5. Оновити сторінку каталогу без кешу й перевірити картку: постер і 3D. Якщо кут постера невдалий, завантажити GLB ще раз з `.json`, де змінено `yaw`.

### 4.2 Що робить бот (`scripts/process_inbox.py`)

| Крок | Деталі |
|---|---|
| Resize | текстури до 2048 |
| Спрощення | адаптивне до цілі близько 100 тис. трикутників: ratio = 100000 / трикутники, пропускається, якщо ratio не менше 0,95 |
| Для сайту | WebP q80, weld, simplify, meshopt, результат у `models/<id>.glb` |
| Постер | з проміжного GLB: `dequantize`, потім `poster.py`, результат `posters/<id>.webp` (800x1000) |
| Каталог | запис у `catalog.json` оновлюється за `id`, сирі файли з inbox видаляються |

Одна погана модель не зупиняє решту, але workflow тоді завершується помилкою. Модель має мати колірну текстуру, інакше постер не побудується.

### 4.3 Видалення моделі (поки вручну)

Одним комітом: прибрати запис із `catalog.json` і файли `models/<id>.glb`, `posters/<id>.webp`. Місце в історії git файли при цьому не звільняють.

### 4.4 Ручний шлях (запасний)

`scripts/optimize.sh raw.glb models/<id>.glb`. Постер: `python3 scripts/poster.py <проміжний.glb> 140 posters/<id>.webp`, де проміжний файл спершу пропускають через `gltf-transform resize` і `dequantize`. Потрібні Node 18+, `numpy`, `trimesh`, `pillow`. Запис у `catalog.json` додається вручну.

## 5. Перевірені висновки і пастки

| Висновок | Підстава |
|---|---|
| `model-viewer` **не вмикає декодер meshopt за замовчуванням**. Без `customElements.get('model-viewer').meshoptDecoderLocation = <url>` GLB зі стисненням не відкривається, видно лише постер | документація `modelviewer.dev/examples/loading` і код пакета 4.3.1; після додавання налаштування модель запрацювала |
| Встановлено `meshoptimizer@0.25.0`: у версіях 1.x файлу `meshopt_decoder.js` немає | перевірено списком файлів пакета |
| Бібліотека закріплена на `model-viewer@4.3.1`: версія 4.4.0 вийшла 2026-10-09, на момент створення це менше двох тижнів | `npm view` |
| Постер із оптимізованого GLB виходив бежевим шумом. Причина: оптимізований файл зберігає UV як `uint16 normalized` (`KHR_mesh_quantization`), а `trimesh` нормалізацію не застосовує. Виправлено: `gltf-transform dequantize` перед постером і пряме читання кольорової текстури в `poster.py` | виявлено наскрізним тестом; після виправлення повторено на GitHub, постер збігся з локальним рендером байт у байт, регресія на сирому GLB результат не змінила |
| Через сайт GitHub можна завантажити **файл до 25 МіБ**, через командний рядок до 100 МіБ, далі потрібен Git LFS | документація GitHub «Adding a file to a repository» |
| Спотворений напис на одній бічній грані є в самій текстурі від Meshy, не наслідок спрощення | рендери оригінальної й спрощеної сітки однакові |
| Дрібний текст на упаковках і нижня частина стенда розмиті | обмеження AI-текстур, оптимізацією не лікується |
| Після коміту бота збірка Pages проходить успішно; явний крок запиту збірки через API лишається в workflow з `continue-on-error`, чи він потрібен, не з'ясовано (на коміт бота бувало по два запуски збірки, один скасовано) | журнал запусків |
| Версії дій у workflow: `checkout@v6`, `setup-node@v6`, `setup-python@v6` | обрані за станом на жовтень 2026: Node 20 для дій замінюється на Node 24 |

Не виправлялось: початок координат моделі по центру, а не внизу (для Nurofen min Y -0,95, max +0,95). Постер зроблений простим програмним рендером (пласке освітлення, без normal map), тому виглядає плоскіше за живу модель.

## 6. Середовище і доступи

- Токен для запису в репозиторій має права на `Contents`, `Actions` і `Workflows`. Спершу запис у `.github/workflows/` повертав 403, після розширення прав працює.
- Через GitHub-конектор можна читати файли, комітити, керувати гілками, дивитися й запускати Actions. Великі бінарні файли через чат не передаються, тому вони йдуть через завантаження власником на github.com (до 25 МіБ).
- Браузера в середовищі агента не було: вигляд сторінки перевірявся за скріншотами власника, а постери й моделі рендерились програмно. Це слабке місце перевірки, тож варто просити скріншоти.

## 7. План перенесення в EquipLens (для іншого агента)

**Перш ніж щось змінювати в `Konst-Andre/equiplens`, прочитати його правила.** Репозиторій має власне ядро правил `Konst-Andre/lens-governance` і гейт-валідатор: він звіряє файли `lens/`, `sessions/`, `tools/` з `lens/EquipLens_INDEX.md`, і неоголошений файл дає помилку. Порядок читання описано в README того репозиторію (`Lens_start.py`, потім черга `lens/EquipLens_CHERGA.md`). З `sandbox` туди нічого не коміттити в обхід цього процесу.

| Факт про EquipLens (з його README та INDEX) | Наслідок |
|---|---|
| Сайт: один `index.html` близько 4 МБ у корені, поряд `data/` і `media/`; Pages публікує корінь | код каталогу доведеться вбудувати в цей один файл, а моделі й постери класти в `media/` |
| У `data/` уже є `catalog.json` (згадано в INDEX, вміст не читався) | наш `catalog.json` назвати інакше (наприклад `models3d.json`), щоб не змішати |
| Сайт має бути PWA | `model-viewer` (близько 1,1 МБ) і декодер meshopt (близько 33 КБ) тепер підтягуються з CDN; для офлайну їх покласти в `media/` або кешувати service worker-ом |

Прикидка шляху (не виконано):
1. Прочитати правила EquipLens і зрозуміти, як там заводиться нова вкладка чи функція (черга, самері, гейт).
2. Вирішити, де живуть моделі: у `media/` застосунку чи в окремому сховищі. Для 40-60 моделей прикидка 60-200 МБ, **не виміряна**.
3. Перенести логіку `render`, `openViewer`, `loadMV` у третю вкладку, зберігши ліниве завантаження (бібліотека і GLB лише після тапу).
4. Кешування для PWA: постери одразу, GLB після першого перегляду.
5. Вирішити, де житиме бот (залишити в `sandbox`/окремому сховищі моделей чи переносити), бо `equiplens` має гейт на нові файли.

## 8. Відкрите і відкладене

**Відкриті питання**
1. Початкова орієнтація камери: яка грань до глядача спочатку, не налаштовано.
2. Кілька `model-viewer` на iOS Safari: у проєкті `model-viewer` є відкрите повідомлення про уповільнення; схема «одна жива модель за раз» його обходить, але на реальному каталозі не перевірялась.
3. Чи не знижує адаптивне спрощення (ціль 100 тис. трикутників) якість на інших моделях (складніші форми, дрібні деталі): перевірено на двох моделях, візуально лише за постерами.
4. Кут постера (`yaw`) підібраний під Nurofen; для інших моделей може потребувати налаштування.
5. Кожен завантажений сирий GLB лишається в історії git навіть після видалення, тож 40-60 моделей по 14-25 МБ можуть помітно роздути репозиторій.
6. Правила компанії щодо показу бренду в каталозі: не обговорювались.

**Свідомо відкладено (рішення власника: робити вже в репозиторії продукту з іншим агентом)**
- *Адмін-режим на сайті* (додавання й видалення без звернення до агента). Обговорений задум: окрема сторінка керування, не вбудована в застосунок; токен GitHub з правами лише на цей репозиторій (fine-grained, з терміном дії), що зберігається в пам'яті браузера; додавання кладе GLB в `inbox/` через Contents API; видалення запускає workflow (`workflow_dispatch` з параметром `remove=<id>`), який одним комітом прибирає запис і файли; підтвердження перед видаленням. Ризики: токен у браузері, CORS і ліміт розміру запису через API не перевірялись.
- *Режим «олівця»* для правки назви й бренду на сайті (не критично).
- *Кращий постер* через headless-браузер зі знімком живого `model-viewer` (не випробувано).

## 9. Як було налагоджено співпрацю з власником

- Мова спілкування: українська. Власник часто диктує повідомлення голосом, тож у тексті бувають помилки розпізнавання (наприклад «коректор» замість «конектор»).
- Власник працює переважно з iPhone, без доступу до комп'ютера: інструкції мають бути виконувані з телефону.
- Він просить спершу показати аналіз і висновки, а дії (створення файлів, коміти) виконувати після його підтвердження; для вже узгоджених планів делегує виконання.
- Він цінує перевірені факти з джерелами й чесний поділ на «перевірено» і «не перевірено»; помилки агента треба визнавати й виправляти, не замовчувати.
- Мета автоматизації: не залежати від ліміту чату щоразу, коли потрібно додати модель.
