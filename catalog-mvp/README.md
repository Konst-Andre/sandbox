# EquipLens: тестовий MVP 3D-каталогу обладнання

> **Тимчасове сховище.** Остаточний дім цього коду і моделей: третя вкладка застосунку EquipLens, репозиторій [`Konst-Andre/equiplens`](https://github.com/Konst-Andre/equiplens). Тут усе лежить окремо, щоб випробувати підхід, не чіпаючи продукт.

## 1. Що це і навіщо

**EquipLens** — польовий нотатник потреби в обладнанні аптек (PWA, один HTML-файл). Третя вкладка має бути **каталогом обладнання**: які типи мерч-обладнання існують для кожного бренду, щоб представник міг зайти й побачити, як воно виглядає.

**Ціль MVP:** перевірити, що 3D-модель обладнання (згенерована в Meshy з фото) можна показати на телефоні: з прийнятною вагою, нормальним завантаженням і обертанням пальцем. Каталог розрахований на 40–60 типів обладнання, тому головне правило: **у сітці лише картинки, 3D вмикається для однієї моделі за тапом**.

Сторінка на Pages: `https://konst-andre.github.io/sandbox/catalog-mvp/` (адреса за стандартною схемою Pages).

## 3. Структура папки

| Шлях | Роль |
|---|---|
| `index.html` | уся логіка: `render()` будує сітку, `openViewer()` створює живий `<model-viewer>`, `loadMV()` підтягує бібліотеку при першому відкритті |
| `catalog.json` | дані каталогу: `id`, `brand`, `name`, `glb`, `poster`, `sizeMB`. Додати обладнання = додати запис |
| `models/` | оптимізовані GLB |
| `posters/` | WebP-постери для сітки (близько 59 КБ) |
| `scripts/optimize.sh` | оптимізація GLB з Meshy для вебу |
| `scripts/poster.py` | програмний рендер постера (див. застереження в розділі 4) |
| `scripts/process_inbox.py` | обробка сирих GLB з `inbox/` (використовує workflow, див. розділ 9) |
| `inbox/` | вхідна папка для сирих GLB |

Відкривати лише через http(s), не як `file://`: `fetch('catalog.json')` і завантаження GLB з файлу не працюють.

## 4. Як додати нову модель (вручну)

1. У Meshy експортувати **GLB**. Текстура 4K і 2K коштують однаково, тож генерувати можна в 4K, а для сайту зменшувати.
2. Оптимізувати: `./scripts/optimize.sh raw.glb models/<id>.glb`. Кроки: resize 2048, WebP q80, weld, simplify (ratio 0.25, error 0.001), meshopt. На Nurofen: **34,2 МБ → 1,5 МБ**, 429 334 → 107 330 трикутників.
3. Постер: `scripts/poster.py` читає лише GLB з текстурами JPEG без meshopt (інакше `trimesh` не відкриє). Перевірено тільки на проміжному файлі: `gltf-transform resize raw.glb t.glb --width 2048 --height 2048`, потім `simplify` з тими ж параметрами. Запуск: `python3 scripts/poster.py t.glb 140 posters/<id>.webp` (140 — кут огляду, підбирати під модель). Потрібні `numpy`, `trimesh`, `pillow`.
4. Додати запис у `catalog.json`.
5. **Дивитися на результат**, а не довіряти скрипту: параметри спрощення перевірені лише на одній моделі.

## 5. Перевірені висновки (читати перш за все)

| Висновок | Підстава |
|---|---|
| `model-viewer` **не вмикає декодер meshopt за замовчуванням**. Без `customElements.get('model-viewer').meshoptDecoderLocation = <url>` GLB зі стисненням не відкривається, видно лише постер | документація `modelviewer.dev/examples/loading` і код пакета 4.3.1. Після додавання налаштування модель запрацювала |
| Встановлено `meshoptimizer@0.25.0`: у версіях 1.x файлу `meshopt_decoder.js` немає | перевірено списком файлів пакета |
| Бібліотека закріплена на `model-viewer@4.3.1`: версія 4.4.0 вийшла 2026-10-09, на момент створення це менше двох тижнів | `npm view` |
| Спотворений напис на одній бічній грані **є в самій текстурі від Meshy**, а не наслідок спрощення | рендери оригінальної й спрощеної сітки однакові |
| Через сайт GitHub можна завантажити **файл до 25 МіБ**, через командний рядок до 100 МіБ, далі потрібен Git LFS | документація GitHub «Adding a file to a repository». Сирий GLB 4K (34 МБ) через браузер не пройде |
| Дрібний текст на упаковках і низ стенда розмиті | обмеження AI-текстур, не лікується оптимізацією |

Не виправлялось: початок координат моделі по центру, а не внизу (min Y −0,95, max +0,95). Постер зроблений простим рендером (пласке освітлення, без normal map), тому виглядає плоскіше за живу модель.

## 6. План перенесення в EquipLens (для іншого агента)

**Перш ніж щось змінювати в `Konst-Andre/equiplens`, прочитати його правила.** Репозиторій має власне ядро правил `Konst-Andre/lens-governance` і гейт-валідатор: він звіряє файли `lens/`, `sessions/`, `tools/` з `lens/EquipLens_INDEX.md`, і неоголошений файл дає помилку. Порядок читання описано в README того репо (`Lens_start.py`, потім черга `lens/EquipLens_CHERGA.md`). З цього репозиторію (`sandbox`) туди нічого не коміттити в обхід цього процесу.

Що відомо про EquipLens (з його README та INDEX на момент створення цього документа):

| Факт | Наслідок |
|---|---|
| Сайт: один `index.html` (близько 4 МБ) у корені, поряд `data/` і `media/`; Pages публікує корінь | код каталогу доведеться **вбудувати в цей один файл**, а моделі й постери класти в `media/` |
| У `data/` уже є `catalog.json` (згадано в INDEX, вміст не читався) | наш `catalog.json` **має іншу назву** (наприклад `models3d.json`), щоб не змішати з наявним |
| Сайт має бути PWA | `model-viewer` (1,1 МБ) і декодер meshopt (близько 33 КБ) підтягуються з CDN; для офлайну їх треба або покласти в `media/`, або кешувати service worker-ом |

Прикидка шляху (не виконано):
1. Прочитати правила EquipLens і зрозуміти, як там заводиться нова вкладка/функція (черга, самері, гейт).
2. Вирішити, де живуть моделі: у `media/` самого застосунку чи в окремому сховищі (з огляду на розмір 40–60 моделей, прикидка 60–200 МБ, **не виміряна**).
3. Перенести логіку `render`/`openViewer`/`loadMV` у третю вкладку, зберігши ліниве завантаження: бібліотека і GLB тільки після тапу.
4. Кешування для PWA: постери одразу, GLB після першого перегляду.

## 7. Відкриті питання

1. Початкова орієнтація камери: яка грань до глядача спочатку, не налаштовано.
2. Кілька `model-viewer` на iOS Safari: у проєкті `model-viewer` є відкрите повідомлення про уповільнення; схема «одна жива модель за раз» його обходить, але на реальному каталозі не перевірялась.
3. Чи не знижує параметр спрощення (ratio 0.25) якість на інших моделях (складніші форми, дрібні деталі).
4. Як вирішується питання зі згадкою бренду в постері/каталозі з погляду правил компанії: не обговорювалось.

## 8. Передумови автоматизації через GitHub Actions

Мета: власник кладе сирий GLB у папку-вхід, workflow сам оптимізує його, робить постер і додає запис у каталог. Обмеження, відомі на зараз:

- Сирий GLB 4K важить близько 34 МБ, а через браузер GitHub приймає до 25 МіБ. Потрібен експорт з меншою текстурою (проміжний файл 2K у моїх тестах був близько 14 МБ) або інший шлях доставки.
- `scripts/poster.py` дає плаский рендер. Для кращого постера потрібен headless-браузер зі знімком живого `model-viewer`: це не випробувано.
- Файли в `.github/workflows/` через GitHub-конектор потребують окремого дозволу токена, тож їх, можливо, доведеться додавати вручну.
- Чи перезапускає збірку Pages коміт, зроблений самим workflow, не перевірено.

## 9. Автоматизація: inbox-workflow

**Як користуватись:** покласти сирий GLB у `catalog-mvp/inbox/` (правила імен в `inbox/README.md`). Workflow `.github/workflows/catalog-inbox.yml` запускається на push у цю папку, обробляє файли, комітить результат у `models/`, `posters/`, `catalog.json` і видаляє сирі файли з inbox.

**Що перевірено:** `scripts/process_inbox.py` запускали локально на сирому GLB Nurofen (34,2 МБ): 429 334 → 99 988 трикутників (адаптивний ratio до цілі 100 тис.), GLB 1,5 МБ, постер 48 КБ, запис у `catalog.json`, сирі файли видалено.

**Що НЕ перевірено:** сам запуск workflow на GitHub (версії дій `checkout@v6`, `setup-node@v6`, `setup-python@v6` обрані за станом на жовтень 2026, бо Node 20 для дій замінюється на Node 24); крок запиту збірки Pages через API (`continue-on-error`); поведінка при великих сирих файлах.

**Ризики:** (1) кожен завантажений сирий GLB лишається в історії git навіть після видалення, тож 40–60 моделей по 14–25 МБ можуть помітно роздути репозиторій; (2) кут постера (`yaw`) підібраний під Nurofen і для інших моделей його, імовірно, доведеться задавати; (3) модель без текстури колірного каналу постер не побудує, workflow завершиться помилкою для цього файлу.
